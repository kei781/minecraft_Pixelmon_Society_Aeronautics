# 원격 접속 후 ALI 툴팁 등록 오류

원래 전체 클라이언트에서 원격 N100 서버로 접속하면 ALI의 거래 위젯 생성 중
`TooltipNode.empty()`가 null 서버 레지스트리를 조회해 NPE가 났다.
빈 노드 조회만 고친 중간 빌드에서는 다음 `TooltipBuilder.build()`가 같은 이유로 실패했다.
두 실제 오류와 중간 결과를 보존했다.

자체 클라이언트 전용 모드는 두 생성 함수의 캐시 조회 한 곳씩을 보정한다.
물리 클라이언트에서 서버 레지스트리가 없고 기존 클라이언트 레지스트리가 있으면
그 원래 캐시를 쓴다. 나머지는 원래 서버 레지스트리 조회를 그대로 호출한다.
네이티브 노드 생성·키·값·플래그·자식·캐시 재사용·인코딩/디코딩의 본문은 바꾸지 않는다.
새 대체 캐시나 더미 노드, 거래 제거, 예외 무시는 사용하지 않는다.

팔레트의 실제 조회·추가·인코딩·디코딩·정리 여섯 메서드에 같은 객체의 JVM 모니터를
적용하고, EMI의 `registerData` 전체도 그 모니터 안에서 실행한다. 수신 테이블을
해석한 뒤 위젯을 만드는 동안 다른 등록 작업이 테이블 세대를 바꾸지 못하게 한다.
원래 메서드 본문은 그대로 호출하며 예외도 그대로 전파한다. 디코딩 내부의 노드 추가는
같은 스레드에서 재진입할 수 있다. 실제 실행에서 여섯 메서드의 synchronized 플래그와
등록 작업의 모니터 보유를 별도 진단기로 관찰한다.

고정 ALI 바이너리에서 관련 서버 캐시 참조 후보는 세 클래스였다. 클라이언트에서
호출되는 두 생성 경로를 수정했고, 서버에서 전리품을 인코딩하고 캐시를 정리하는
`AbstractServer`는 그대로 뒀다. 문자열 참조 조사가 모든 동적 호출을 증명하지는 않는다.

## 실제 검증과 설정 보존

### 세션 중 재동기화와 ID 해석

고정 ALI 바이너리 조사에서 `TooltipNodePalette.decode`는 기존 목록과 풀을 비운 뒤
수신 순서대로 전체 테이블을 다시 만든다. 자식 노드는 그 테이블의 앞선 ID를 참조한다.
클라이언트 전용으로 추가한 항목을 다음 수신 데이터 앞에 이어 붙이지 않는다.
서버의 전송은 `AbstractServer`가 테이블을 인코딩한 뒤 원래 캐시를 정리하는 경로다.
클라이언트의 `RequestLootDataMessage`는 본문이 없는 요청이며 툴팁 ID를 보내지 않는다.
고정 바이너리의 직접 참조를 조사한 결과이며 외부 모드의 모든 반사 호출을 증명하지는 않는다.

네트워크 처리는 원시 데이터 조각을 수신해 future를 완료한다. 팔레트 디코딩은
`GenericUtils.processData`를 호출하는 EMI 등록 작업에서 일어난다. 디코딩을 별도의
네트워크 스레드 작업이라고 가정하지 않았다. 원래 팔레트의 목록과 맵에는 잠금이 없어
로컬 생성과 등록이 겹칠 위험이 있으므로 위의 공통 모니터를 적용했다.

검사 도구는 순서대로 모든 노드의 ID·키·값·컴포넌트·의미 플래그·자식 ID를 해시한다.
원문 텍스트는 기록하지 않는다. ALI가 전송 시에만 더하는 번역 인덱스 표시 비트
`0x100`은 따로 개수를 기록하고 내용 해시에서만 제외한다. 해석된 번역 키와 다른
플래그는 모두 비교한다. 처음에는 이 표시 비트를 포함해 서버와 수신본 해시가 달랐고,
그 진단 결과도 보존했다.

별도 N100 QA 서버(운영 서버와 다른 포트·새 폐기용 월드)와 실제 로그인한 Mac
클라이언트에서 30,801개 서버 노드를 비교했다. 첫 수신과 접속을 유지한 ALI 데이터
재요청 뒤의 두 번째 수신 모두 순서·내용 해시가
`564822fc850502cc172577515a13e43fa8ed3191960fd628ff48555f8886b76f`로 같았다.
등록·디코딩은 첫 번째 `Thread-60`, 두 번째 `Thread-170`에서 같은 팔레트 모니터를
보유한 채 실행됐다. 렌더 스레드의 제어 호출도 같은 잠금을 사용했다.
이는 실제 관찰한 경로의 결과이며 가능한 모든 스레드 실행 순서를 시험했다는 뜻은 아니다.

전체 서버 `/reload`도 실제로 실행했지만 합격하지 않았다. Forge 전리품 갱신의
`LootModifierManager.apply` NPE는 시작 때도 발생하고 자체 처리되는 설정 오류였다.
전체 갱신을 중단시킨 예외는 SerializerDebug의 null 플레이어 전송이었다.
실패 기록을 보존하고 ALI의 원래 `reloadLootData()`와 EMI의 원래 `reload()`를 명시적으로
호출해 두 번째 수신을 검증했다. 이때 서버는 기존 인코딩 데이터를 다시 전송했으며,
성공적인 전체 데이터팩 교체나 변경된 새 서버 데이터의 수신으로 기록하지 않는다.
두 서버 갱신 오류는 별도 후속 수정 대상이다. 운영 서버는 중단하지 않았다.

### 실제 주입기와 등록 중 연결 해제

후속 가드는 MixinExtras 0.5.4와 활성 `WrapMethod` 주입기를 필수 생성자에서 확인한다.
이 주입기는 mixin `postApply` 뒤의 확장에서 래핑을 완료하므로, 콜백 비트만으로
완료를 판정하지 않는다. 클래스 정의가 끝난 뒤 원래 메서드·자체 처리기·실제 생성된
private 원본 본문 브리지의 서술자와 수량을 확인하고 별도 완료 래치를 요구한다.
처리기만 병합된 음성 표본은 거부한다. 원래 Forge 래퍼는 독립 modId가 없으므로
존재하지 않는 Forge 모드 의존성을 선언하지 않았다.

원래 ALI·EMI와 자체 보정만 넣은 최소 Forge 클라이언트에서 MixinExtras가 없으면
필수 생성자가 실제로 시작을 거부했다. 전체 모드 구성은 실제 로그인·등록을 통과했다.
QA 관찰기에만 등록 시간을 1초 늘리는 두 가지 검사를 추가했다. 렌더 스레드의 실제
팔레트 읽기는 약 1.23초 기다린 뒤 완료됐다. 다른 검사에서는 등록 중 네이티브 연결을
끊었고, 이후 월드·플레이어 부재를 새 메인 스레드 콜백으로 확인했다. 등록도 끝났으며
ALI 등록 실패와 서버 크래시는 없었다. 이때 마지막 등록은 월드가 비워진 뒤 디코딩 없이
끝났으므로 세 번째 데이터 수신 합격으로 세지 않는다. 클라이언트와 QA 서버는 정상 종료했다.
인위적 지연을 포함한 경합 검사이며 일반 플레이의 무지연이나 모든 교착 가능성을 증명하지 않는다.

수정 전 실제 접속에서 클라이언트 레지스트리는 존재하고 서버 레지스트리는 null이었다.
캐시에 30,804개 노드와 원래 빈 노드가 있었지만 빈 노드 팩터리는 NPE로 실패했다.
수정 후에는 기존 빈 노드 ID 1을 재사용하고 기본·고급 모드 모두 빈 노드로 판정됐다.
일반 빌더의 네이티브 키 전용 제어 표본도 비어 있지 않은 실제 텍스트 컴포넌트를 만들었다.
이는 자체 표시문구 하나의 로컬 캐시 항목이며 게임 아이템·서버 데이터·인증을 합성하지 않는다.
검사 전 존재하던 모든 캐시 ID의 객체 정체성을 검사 후에도 유지했다.

초기 두 생성 함수 보정 빌드(R3)의 첫 관찰에서는 캐시가 30,809개였고 빈 팩터리 호출 뒤에도 같았다.
자체 빌더 표본이 그 뒤 한 항목을 추가했으며 다시 호출하면 같은 ID를 재사용했다. 전체 데이터 등록이
`Data registration finished successfully`로 끝났고 원래의 등록 실패는 없었다.
기존 ALI 전리품 레시피 12,246개와 각 카테고리 수량도 보존됐다.

Society 원본은 `kubejs/assets/emi/recipe/filters/emi.json`에서
`ali:trade_loot`, `ali:fishing_loot`, `ali:hero_loot`를 EMI 결과에서 숨긴다.
그래서 수정 후에도 이 세 카테고리의 최종 레시피 수는 0이다. 이를 임의로 풀거나
레시피 증가를 성공 조건으로 만들지 않았다. 필터 SHA256은
`4b5d8a639a6089c984535f33635dbc5bdb9807f2144f666a5c1eaef9902f15cf`이며
서버·기존 클라이언트·새 팩에서 같은 바이트를 유지한다.
원래 전역 레시피 수만 보던 관찰 도구에 카테고리별 실제 조회도 추가해 이를 확인했다.

원본·중간·최종 기록과 각 진단 빌드는 [증거](../evidence/ali-client-tooltips.json)에 구분한다.
화면 조작은 정상 Prism 실행에만 사용했고, 스타터 선택 화면을 강제로 닫지 않았다.
실제 거래 화면의 육안 검수·단일 플레이·6인 부하·최신 Windows 가져오기는 합격으로
기록하지 않는다. 기존 Connectivity 경고와 ReliableEmi 그룹 오류도 별도 후속이다.

## 패키지와 재생성

서버의 313개 모드·공통 JAR·월드는 이 단계에서 바꾸지 않는다. v18 클라이언트는
기존 v17의 354개 모드에 `PSA-ALI-Client-Compat-0.1.jar` 하나를 더해 355개다.
모드 외에 달라진 것은 가져오기 색인과 프로필뿐이며 기존 payload 7,931개는 같다.
원래 ALI JAR도 그대로다. 진단 attach 도구·계정·세이브는 팩에 넣지 않는다.

현재 호환 JAR는 11,204바이트·11개 항목이며 SHA256은
`0b05990106c46a19aa1c84a91553e14d7e387bc7de2924c9e4b5d02df45c5055`다.
두 독립 준비 환경의 정규화 빌드가 같다. [자체 소스·클래스·입력 고정값](../compat/ali-client-build.json).
최초 후보는 `pack.mcmeta` 누락으로 로딩 오류 화면에 머물러 거부했다.
두 번째 후보는 빈 노드만 고쳐 일반 빌더에서 실패했다. 두 후보 모두 배포 합격이 아니다.

```sh
gradle --offline --no-daemon --max-workers=2 -p /path/to/prepared-forge-workspace \
  -I /path/to/repository/tools/forge-ali-client.gradle \
  -PpsaAliSource=/path/to/repository/compat/ali-client \
  -PpsaAliJar=/path/to/AdvancedLootInfo-forge-1.20.1-1.12.0.jar \
  -PpsaEmiJar=/path/to/emi-1.1.24+1.20.1+forge.jar \
  -PpsaMixinExtrasJar=/path/to/MixinExtras-0.5.4.jar reobfPsaAliClientJar
python3 tools/forge_resources.py canonical-jar \
  /path/to/prepared-forge-workspace/build/libs/PSA-ALI-Client-Compat-0.1.jar \
  /path/to/fresh-ali-client-compat.jar
```

Java 17.0.21·Forge 47.4.20 준비 환경을 사용한다. 필수 모드 생성자는 ALI 해시를
다시 검사하고 네 대상 클래스를 로드한 뒤 네 변환의 적용을 모두 확인한다.
Mixin plugin 초기화 예외가 설정만 빠뜨리고 계속 실행되는 경우도 거부한다.
재사용 가능한 helper/plugin은 mixin 전용 패키지 밖에 두었다.
네이티브 QA 관찰기는 `--kind ali`로 별도 빌드하며 production mod가 아니다.
버전별 클래스 이름을 나눠 이미 로드한 에이전트 클래스를 재정의하지 않는다.
EMI와 MixinExtras는 원래 전체 모드팩에 있던 고정 입력이다. MixinExtras 컴파일 입력은
원래 Quality Food의 중첩 Forge 래퍼 안에 든 common 0.5.4 JAR이며 래퍼 자체가 아니다.
새 런타임 의존성 JAR를 팩에 추가하지 않는다. 입력 해시는 빌드 기록에 고정했다.
내보내기 단계에서도 원래 ALI 대상 파일명과 SHA256을 확인해 누락·변경 시 출력 전에 거부한다.
지원하는 Prism 인스턴스는 게임 디렉터리를 작업 디렉터리로 사용한다. 다른 작업 디렉터리로
시작하는 런처는 이 호환 모드의 상대 경로 가드 때문에 거부될 수 있다.
