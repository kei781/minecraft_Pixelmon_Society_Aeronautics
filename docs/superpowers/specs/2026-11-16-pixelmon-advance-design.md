# Pixelmon base attribute advance

The user delegated implementation choices and requested continuous execution. Preserve 24-chunk view, shader quality, model/animation fidelity and all emitted attributes. Issue #21 and draft PR #22 are the base; the latter's observational world runs did not establish an overall FPS improvement.

The next measured target is BufferBuilder.nextElement: 26.03% of ON render-thread leaf samples. Inspection of the actual 355-mod merged class found the Embeddium implementation with no additional nextElement hooks. Iris adds entity IDs, midpoint and tangent from endVertex HEAD; other emission and batching hooks also remain in endVertex. Do not replace these completion hooks or their arithmetic.

Alternatives considered: GPU skinning/parallel animation needs a much broader ownership and synchronization change; tangent caching needs proof for varying normals and UVs. This iteration instead collapses the six base-attribute transitions into their equivalent final cursor state. This is the implementer's choice within the user's delegation, not a separately user-approved technical design.

Add a second startup opt-in `psa.pixelmon.fastAdvance`, dependent on the existing `psa.pixelmon.fastVertices`. When disabled, its mixin and interface are absent. Validate the exact Iris entity format, the six Embeddium transitions, source/target element identities, fixed-color state and all byte offsets before touching state. Cache the immutable transition plan per element-array identity; recheck source/target identities when used. Then set byte cursor, index, current VertexFormatElement and current Embeddium element to the same values as six original calls. The existing endVertex runs unchanged. Unsupported plans return false without mutation and use the six original calls.

The final low-priority mixin checks the observed merged nextElement bytecode against the pinned Embeddium method before allowing the bypass. An unexpected hook/body disables the authored bypass method. This is a compatibility check at mixin application, not protection against later arbitrary bytecode agents or subsequently applied lower-priority mixins. Such transformations are unsupported; keep this experiment opt-in and draft.

Acceptance: test opt-in combinations and actual pinned bytecode rejection; compare actual Forge builder cursor states and extended output bytes, growth, alternating original/candidate vertices, builder reuse, rejected fixed color/partial/terrain/glyph states; benchmark both flags separately using the same candidate binary. CI and independent Claude review must pass. Kernel speedups remain separate from game FPS. Do not modify the original or currently running playtest, merge, enable by default or claim world visual acceptance.
