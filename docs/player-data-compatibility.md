# 플레이어 데이터 동기화와 같은 유형 조사

이 문서는 Task 6와 6bdf 후보 당시의 구현·검증 기록이다. 해당 보정은 현재 v8에도 포함되며, 새 설치와 서버 짝 버전은 [Windows 안내](windows-client.md)와 [최신 진행 상태](progress.md)를 따른다.

실제 Windows v6 인증 접속에서 반복된 필드 22 오류는 두 모드의 등록 순서 차이였다. 클라이언트의 Carry On `CARRY_DATA_KEY`는 22번 compound, Pixelmon `dwPokeballs`는 23번 string이었다. 서버는 각각 31번 compound와 22번 string이었다. 따라서 서버의 포켓볼 문자열이 클라이언트에서 compound 자리로 들어갔다. 나머지 Pixelmon byte 필드 8개도 한 칸씩 달랐다. 접속이 유지됐다는 사실을 동기화 통과로 세지 않는다.

`PixelmonPlayerDataOrderMixin`은 Pixelmon의 필드를 할당하기 전에 Carry On의 기존 필드 초기화를 완료한다. 번호를 직접 정하지 않으며 패킷을 버리거나 값을 대체하지 않는다. 별도 최소 진단 팩처럼 Carry On이 없으면 보정할 대상도 없다. 원본 Pixelmon·Carry On JAR는 그대로다. 공통 수정이므로 클라이언트와 서버에 같은 수정 포팅 JAR가 필요하다.

전체 공통 JAR 313개의 중첩 라이브러리까지 클래스 70,808개를 검사해 동기화 필드 직접 등록 호출 556곳을 찾았다. 자기 클래스 496곳, 믹신 대상 26곳, 동적 대상 22곳, 외부 클래스 12곳이었다. 클라이언트 추가/대체 JAR 41개의 클래스 8,767개에서는 직접 등록 호출이 없었다. 이는 해당 호출의 정적 검색 범위이며 전체 기능의 무결성을 보장하는 수치는 아니다.

외부 클래스 12곳 중 9곳은 Pixelmon 플레이어 필드, 1곳은 Carry On 필드, 나머지는 More Minecarts 탱크 수레와 Windswept 염소 변종이었다. 동적 호출은 Pixelmon DataSync, Easy NPC, EntityJS로 나뉜다. 헬퍼 호출도 137곳을 추적했다. 이 중 Pokemon·PokemonBase가 AbstractBaseEntity에 할당하는 8곳을 외부 소유 조사 항목에 명시했다. 단순히 DataSync 생성자 이름만 비교하면 이 차이를 놓치므로 실제 초기화 클래스까지 구분해 비교한다. 아직 실행하지 않은 동적 경로를 통과로 기록하지 않는다.

최종 공통 313 JAR의 클래스 70,810개와 실제 선택된 전체 클라이언트 354 JAR의 클래스 79,461개도 다시 검사했다. 메서드 참조와 Handle 상수 형태의 할당 참조는 모두 0곳이며, 별도 양성 대조에서 두 형태를 모두 검출했다. 앞의 70,808개·8,767개는 v6 및 클라이언트 추가/대체 후보의 최초 조사 수치다.

추가 발견된 More Minecarts 1.8.3의 `TankCartEntity.FLUID_TAG`는 자기 클래스 대신 형제인 `FlagCartEntity`에 등록됐다. 원본 전체 팩의 두 초기화 순서에서 flag/tank 필드 번호가 14/15와 15/14로 바뀌는 것을 재현했다. `TankCartDataOwnerMixin`은 정확한 등록 호출 한 곳의 클래스 인수만 자기 클래스로 고친다. 기본 NBT나 액체 값은 바꾸지 않는다. Windswept 염소와 Pixelmon의 외부 소유 헬퍼 필드는 양쪽에서 반드시 관찰해야 할 대상으로 지정했다. 실제 Windows 내부의 강화된 비교기로 서버 기준표와 대조한 결과, 이들을 포함한 관찰 owner 339개가 모두 일치했고 필수 누락·한쪽 전용 owner도 없었다. 기준표는 같은 공통 모드를 쓰는 Mac 전용 서버의 추적이며 N100 전체 추적이라고 표현하지 않는다.

N100에서는 인증 접속 뒤 임시 읽기 전용 KubeJS 관찰 스크립트로 실제 초기화된 Player 필드 10개의 번호·자료형을 직접 확인했다. 강제 초기화 순서 옵션이나 진단 JAR 없이 Carry On 22/compound, Pixelmon 23/string·24~31/byte였다. 관찰 스크립트는 제거했고 원래 서버 스크립트 188개가 오류 없이 다시 로드됐다. [자연 순서 관찰](../evidence/n100-natural-player-schema.json).

시험용 `psacatalogprobe`는 전체 등록 목록, 기본 아이템 스택 저장·복원, 필드 번호와 자료형, 선택한 초기화 순서를 기록한다. 각 시험은 별도 루프백 프로필에서 실행하며 끝에 정상 저장·종료한다. 모드팩의 버전 확인 스레드가 뒤늦게 종료되는 경우가 있어 결과 파일·완료 표식·FAILED 부재와 프로세스 종료를 각각 확인한다. 값·인증 정보는 스키마에 기록하지 않는다. 이 모드는 이용자 내보내기에 포함하지 않는다.

진단 0.4는 Forge LoggingIn/LoggingOut 이벤트로 접속 세션을 세고, 리스폰·차원 이동으로 LocalPlayer가 교체되는 경우에는 같은 세션의 별도 스냅샷으로 구분한다. 앞서 Windows에 쓴 0.3의 파일 번호는 재접속 근거로 사용하지 않았다. 실제 N100 인증 접속 2회와 중간 연결 종료 로그, Windows 화면의 포켓몬·인벤토리 보존으로 재접속을 확인했고 두 접속에서 타입 오류·패킷 처리 실패는 0건이었다.

추가 Windows 실행에서 0.4의 두 세션 파일도 같은 JVM 안에서 각각 생성됐다. 공통 JAR 313개의 실제 해시 집합은 N100과 같았다. 설치 확인 시각 이후 지정 Windows 장치에서 온 실제 인증 접속 4건을 서버 로그로 대조했다. 비교 입력·비교기·세션 파일의 해시는 [주소·계정 없는 집계 기록](../evidence/windows-entity-data-verification.json)에 연결했다. Ubuntu 컨트롤러 검사 56개는 모두 통과했다. 탱크 UI가 서버 물 1,000mB를 0mB로 표시하는 별도 문제와 전체 콘텐츠·플레이 검증은 계속 남아 있다.

기본 스택 17,239개 왕복 검사는 실제 화면 표시나 사용 검사가 아니다. 등록 블록 12,804개와 엔티티 유형 547개도 다음 단계의 목록이다. 폐기 가능한 N100 QA 월드에서 소량씩 소환·표시·사용을 검사하고 발견한 장애 유형을 다시 전수 조사한다. 원래 플레이 월드는 별도 백업과 프로필로 보존한다. 실제 포획·전투, Society 경제·진행, Aeronautics 조종 비행과 6인 부하의 전체 완료 여부는 별도 기록한다.
